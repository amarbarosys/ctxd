# S2: fold policy

`src/ctxd/fold.mojo` runs on the request path of `/v1/messages` and `/v1/chat/completions` (not `count_tokens`).
Without `[summarizer] url` in `ctxd.toml` nothing is folded and the S0 passthrough is unchanged.

## Config (`ctxd.toml` or env)
```
[window]       messages = 200000   chat = 128000       # tokens, per upstream (CTXD_WINDOW_MESSAGES / _CHAT)
[summarizer]   url = "http://host:port/base"  model = "..."  max_tokens = 1000   # POST <url>/v1/chat/completions
```
Summarizer bearer key: env `CTXD_SUMMARIZER_KEY` (optional). Nothing else is hardcoded except `K = 6`.

## Per request
1. Session id: header `x-ctxd-session`, else FNV-1a of the system prompt plus the messages up to the first user message.
   Store: `~/.cache/ctxd/<id>/` (S1). The delta beyond what the store holds is appended. If the store holds more
   messages than the request, or its first or last message differs, the history diverged: forward unchanged, log `FOLD-SKIP`.
2. The messages are rebuilt with every stored fold in place of its range. Placeholder, built only from the store record:
   `{"role":"user","content":[{"type":"text","text":"[ctxd fold <id>: msgs a-b]\n<summary>"}]}`, b inclusive.
   The fold record in `log.bin` is `<cache_control object or empty>\n<placeholder text>`; the object is the last
   `cache_control` found in the folded block.
3. Estimate = body bytes / 4. Over 0.8 W: fold `[a, b)`, `a` = end of the last fold (or after leading `system` messages),
   `b` the smallest tool-pair-safe cut, at most `n - K`, that brings the estimate under 0.5 W (the largest safe cut if none does).
   A cut in front of message m is safe if m has no `"type":"tool_result"` and no `"role":"tool"`.
   "Turn" for K means message.
4. The summarizer is called synchronously through curl. Any failure (curl, HTTP != 200, empty text, no safe cut, diverged
   history) forwards the original bytes and logs `FOLD-SKIP <reason>`. A fold logs `FOLD <sid> id N msgs a - b est X -> Y us T`.

Bytes: a request that needs no rewrite (no fold stored, under 0.8 W) goes out as the client sent it. Once a session has a
fold, bodies are re-serialized by bento's `Json.dumps` (compact, `ensure_ascii`), which is deterministic, so bytes in
front of the live tail are stable between folds.

Check: `tests/gate-s2.sh`.
